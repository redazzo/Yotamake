How it works

How a change moves through Yotamake, and which parts are enforced by hooks. Each skill's SKILL.md holds its exact rules, and the README holds the full detail.

The plugin and the repository

Yotamake is split in two. The plugin holds the method and is the same for every project. Each repository holds the facts that are specific to it.

Lives inWhatWho changes it
The pluginSkills, hooks, output style, the installer and its templateYotamake; reaches every project on update
Each repositoryCLAUDE.md facts, scripts/check, docs/, hook config, CIThe project
Each repository, harness-ownedThe docs scripts, the pre-commit hook, the session scripts, the version fileRefreshed by the installer

Skills read project facts only from named CLAUDE.md sections, such as Checks or Deploying. When a section is missing, the skill says so and uses a stated default, or stops and asks.

A session, step by step

A session is one branch and one merge that fits in one context. It is what simple-session runs for every change to code, tests or docs.

  1. Check the size

    Before branching. A change that adds a migration and other code, adds more than one interface, touches more than one package, needs an ADR, or would need a /clear is too big. Claude offers a multi-session plan instead.

  2. Branch

    Cut a branch from main with a prefix such as feat/ or fix/. Never edit on main.

  3. Design and reuse

    Look for code to reuse, and check the change against Architecture. Stop and ask on a conflict.

  4. Do the work

    Keep to one concern. Update the doc that owns what changed. With Test-first: yes, start with a failing test. A bug fix follows the debugging skill.

  5. Run the checks

    Run scripts/check. Never skip or weaken a check to get a pass.

  6. Review

    Once, on the whole branch: the built-in /simplify, a design read by a fresh agent, and /code-review. Docs-only and trivial branches skip it.

  7. Stop and report

    What changed, what was reused, which docs were updated, the check and review results, and a proposed commit message. Then ask: commit and merge?

On a yes, Claude commits, bumps the version if the project uses bumps, and merges locally, or pushes and opens a pull request if the project works that way. It never deploys.

Bigger work

Work that will not fit one context runs as multi-session: numbered sessions with a working folder that survives /clear. The folder is git-ignored at .scratchpad/<date>-<slug>/, or committed under .sessions/ in a cloud session. It holds the plan, findings and a log.

  • S0 plans. It hands its reading to agents, one per area, so the main context keeps room for the plan. You approve the plan before S1.
  • Resume after /clear with "Read .scratchpad/<folder>/README.md and start the next session."
  • Parallel sessions. Two sessions that change different files and need nothing from each other can run at once, each in its own git worktree, and merge one at a time.
  • Autopilot. Say "run autopilot" and the remaining sessions each run in a fresh agent. It ends with one report and one question: merge? Nothing is pushed or merged without your yes.

Design and reuse

The Architecture section of CLAUDE.md has six lines the skills read:

LineSays
StyleThe overall shape, for example layered, hexagonal, or a plugin.
ModulesWhich folder owns what.
BoundariesWhat may not import or call what.
Shared codeWhere to look before writing something new.
PatternsHow recurring things are done: errors, config, data access.
ConstraintsHard limits: runtime versions, budgets, licences, security rules.

A full install adds the accepted ADRs in docs/decisions/. /yotamake:setup proposes the six lines from the repository, using a catalogue of styles.

Before any edit, Claude searches for code to reuse. It stops and asks when a change would break a boundary or a constraint, go against an ADR, or bring in a pattern or a dependency the project does not use. It does this even when told not to ask, because changing the rule is a separate decision.

The one gate

scripts/check is the only list of checks. It belongs to your project. Add a check by editing the script.

CommandRunsUsed by
scripts/checkEvery check for what changed since main, plus uncommitted workClaude, before proposing a commit
scripts/check --stagedFast checks on staged filesThe pre-commit hook
scripts/check --allEvery checkCI

It prints one PASS or FAIL line per check. A person's commit passes the same gate as Claude's. One catch: core.hooksPath is a local git setting and is not cloned. A SessionStart hook sets it at a teammate's first Claude Code session in the clone. Someone who never opens Claude Code there runs git config core.hooksPath .githooks once. CI covers everyone.

Stop points

The skills stop before commit, version bump, merge and deploy. The repository's settings back this up: git commit, merge, push, rebase, reset --hard and tag are under ask, so Claude Code asks every time. An ask rule wins over a matching allow rule, even a broad one. Add your deploy command to the list too.

Cutting a branch, staging files and a fast-forward pull are allowed, so they do not prompt.

The hooks

HookWhat it does
pre-edit-protectBlocks edits to the files listed in protected-paths.conf. By default that is .env files, keys and certificates.
pre-edit-main-branchBlocks Edit and Write while the repository is on its main branch.
pre-bash-gitBlocks --no-verify, and git commit on the main branch.
post-edit-checkRuns a fast per-file check after each edit, from post-edit-checks.conf.
post-edit-markNotes that this session edited a code file.
stop-check-ranBlocks the end of a turn once when code changed and scripts/check has not passed since. A second stop goes through, so Claude can still stop to ask a question.
session-upgradesAt session start, says when the repository's harness is older than the plugin.

The repository also has two SessionStart hooks of its own, which work without the plugin. One sets core.hooksPath. The other tells Claude the branch, any active multi-session effort, and that every change runs as a session.

A repository that works on main on purpose can opt out with an empty file at .claude/yotamake/allow-edits-on-main. A person creates it; Claude cannot.

What the hooks do not cover

The edit hooks watch the Edit and Write tools only. The Bash hook watches git commands only. So a shell command gets past them: sed -i, echo > .env, or a code change made from the shell, which the Stop hook never sees. Claude Code's own permission prompt for Bash is the guard there.

The docs system

A full install adds four kinds of doc under docs/, each with its own update rule:

  • Reference: how the system works now. Corrected in place.
  • Guides: how to do a thing. Corrected in place.
  • Decisions: why it is built this way. Never edited, only superseded.
  • Records: what was done, and when. Written once.

Plus docs/backlog.md for open work, each item with the trigger that should make someone pick it up.

When two docs disagree: code beats decisions, decisions beat reference, reference beats records. Each subject has one owning doc, named in the "Owns" table in docs/README.md. A change in behaviour updates that doc on the same branch.

The linter fails on broken links, docs nothing links to, bad front-matter and a stale records index. For a repository with existing link debt, node scripts/docs/lint-docs.mjs --update-baseline records it once, and after that only new problems fail.

Evals

The plugin has an eval suite: over twenty cases, each run against a small project built fresh with the harness installed. They check behaviour such as "branches before editing", "refuses a change that is too big", "reuses the shared helper", and "stops at a boundary even when told not to ask". The headline number is the score with the plugin minus the score without it. The README's eval table lists every case.
